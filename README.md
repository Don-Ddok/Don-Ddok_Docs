# 브랜치 전략 (Branching Strategy)

이 레포지토리는 **문서(문서/노트/자료)만 관리하는 저장소**입니다. 코드 배포가 없으므로 복잡한 브랜치 전략 대신, 문서의 이력 관리와 검토 절차에 초점을 맞춘 단순한 흐름을 사용합니다.

## 1. 기본 원칙

- `main` 브랜치는 항상 "확정되어 게시 가능한" 문서 상태를 유지한다.
- 문서를 새로 작성하거나 수정할 때는 `main`에서 브랜치를 파서 작업한다.
- `main`에 직접 push하지 않는다. (오탈자 등 사소한 수정은 예외로 허용 가능)
- 작업이 끝나고 병합되면 브랜치는 삭제한다.

## 2. 브랜치 종류 및 네이밍

| 브랜치 타입 | 용도 | 네이밍 규칙 | 예시 |
|---|---|---|---|
| `main` | 게시 가능한 최종 문서 상태 | - | `main` |
| `docs/*` | 신규 문서 추가 | `docs/문서주제` | `docs/branching-strategy` |
| `update/*` | 기존 문서 수정/보완 | `update/문서주제` | `update/api-spec` |
| `fix/*` | 오탈자, 잘못된 정보 수정 | `fix/문서주제` | `fix/typo-readme` |

- 브랜치명은 소문자 + 하이픈(`-`)만 사용한다.
- 문서 하나(또는 주제 하나)당 브랜치 하나를 기본으로 한다.

## 3. 작업 흐름

1. `main`에서 최신 상태로 pull 받는다.
   ```bash
   git checkout main
   git pull origin main
   ```
2. 목적에 맞는 브랜치를 생성한다.
   ```bash
   git checkout -b docs/branching-strategy
   ```
3. 문서를 작성/수정하고 커밋한다. (커밋 컨벤션은 4번 참고)
4. 원격에 push하고 PR을 생성한다.
5. 리뷰(맞춤법, 내용 정확성, 포맷 확인) 후 `main`으로 병합한다.
6. 병합 후 브랜치를 삭제한다.

> 혼자 운영하는 레포라면 PR 없이 바로 `main`에 커밋해도 무방하지만, 이력을 남기고 싶다면 위 흐름을 그대로 따르는 것을 권장한다.

## 4. 커밋 메시지 컨벤션

```
<type>: <내용>
```

| type | 설명 |
|---|---|
| `docs` | 새 문서 추가 |
| `update` | 기존 문서 내용 수정/보완 |
| `fix` | 오탈자, 링크 깨짐 등 사소한 오류 수정 |
| `remove` | 문서 삭제 |
| `chore` | 폴더 구조, 템플릿 등 문서 외 설정 변경 |

**예시**

```
docs: 브랜치 전략 문서 추가
update: API 명세서에 에러코드 표 보완
fix: README 오탈자 수정
```

## 5. 폴더/파일 구조 (권장)

문서가 늘어날 것을 대비해 주제별 폴더로 정리한다.

```
/docs
  /convention      # 컨벤션 관련 문서
  /architecture    # 구조/설계 문서
  /meeting-notes   # 회의록
README.md          # 전체 문서 목록 및 안내
```

## 6. PR 규칙 (협업 시)

- 제목: `[type] 문서명 요약` (예: `[docs] 브랜치 전략 문서 추가`)
- 본문에는 변경/추가한 문서의 목적과 주요 내용을 간단히 적는다.
- 여러 명이 함께 관리한다면 최소 1명의 리뷰 승인 후 병합한다.
- 병합 방식은 **Squash and Merge**로 통일해 히스토리를 깔끔하게 유지한다.
